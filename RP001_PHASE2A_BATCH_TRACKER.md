## Batch 8 — Resolution (2026-08-02) + acquisition-tooling bug fix

**Tooling bug found and fixed:** the first pass at Batch 8 hit a ~236-request run of non-quota failures (HTTP status -1, "unknown" error -- consistent with a mid-run connectivity outage on this machine during an unattended multi-hour background wait, not an API-side problem: a direct follow-up request confirmed both connectivity and quota were fine immediately after). `rp001_batch_acquire.py`'s original loop only paused (return 2) on an explicit HTTP 402; any other failure type was logged to `failed_queue.csv` per-item but the loop kept going, and once every `todo` item had been *attempted* (success or not), the script proceeded straight to the Integrity Gate over a batch that was actually only 34% complete (124/360 requests genuinely succeeded). This didn't produce a false anomaly finding -- the gate only reads files with real row data, so incomplete/failed downloads were silently skipped rather than misread -- but it would have let an incomplete batch be marked PASS or STOP and moved past, undercounting real coverage. **Fixed:** `run_batch` now also returns PAUSED (2) whenever any non-402 failures remain, so the next invocation's skip-existing logic retries exactly those pairs before the Integrity Gate is allowed to run. Batch 8 was then re-driven to a genuinely complete 360/360 state before its gate result (below) is reported. This fix is acquisition-tooling only -- no change to F_INST_01, normalization, horizon, or the break interval.

**Raw Integrity Gate result: STOP** on one condition — Dealer recurrence INSIDE the locked break window, 7 stocks (6614, 6722, 6831, 6908, 6934, 7610, 7711). Investigated individually (see `RP001_PHASE2A_DEVIATION_LOG.md` D-05 Batch-8 addendum): all 7 follow the now-established pattern (a stock-specific `Dealer`→split-category cutover date, with the entire or partial break window on the pre-cutover side), and all 7 show `Foreign_Investor` present on every date that carries any institutional row at all -- zero exceptions. This batch's stock range (~6449-7711) also runs materially sparser overall (88/120 stocks over the 10% missing-rate warning threshold, vs. 20-40% in prior batches) -- expected for smaller/newer-listing issuers, governed by the Missingness Policy's coverage gate, not a new anomaly type. F_INST_01/H-C1–H-C5 unaffected; resolved non-escalating.

## Batch 9 — Resolution (2026-08-02) + second acquisition-tooling bug fix

**Tooling bug found and fixed:** Batch 9's driver got stuck retrying the same 10 (dataset, stock_id) pairs across 5 attempts and ~5 hours of real time. Root cause: `TaiwanStockPER` returns a legitimate HTTP 200 with zero rows for several TDR-style codes (9103, 9105, 9110, 9136, 910322, 910861, 911608, 911622, 911868, 912000) — confirmed by a direct follow-up request outside the pipeline. `rp001_batch_acquire.py` recorded this correctly as `status="empty"` in the manifest, but then also (a) added it to `failed_queue.csv` for retry, since the queueing check was `status != "success"` rather than `status == "failed"`, and (b) never counted it as resolved in `load_existing_success()`, which only recognized `"success"`. The result: an unresolvable infinite retry loop, since the API will always return the same empty (but valid) answer. **Fixed:** `load_existing_success()` now also treats `"empty"` as a resolved terminal state (not retried), and only genuine `"failed"` rows (non-200 / exception) get queued for retry. Also cleaned up 391 duplicate manifest rows that accumulated from the stuck retry loop across Batches 1-9 (kept the last/final-state row per (batch_id, dataset, stock_id) — no information lost, since duplicates were byte-identical repeat downloads). Acquisition-tooling only; no change to F_INST_01, normalization, horizon, or the break interval.
